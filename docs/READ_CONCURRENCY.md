# 조회 병렬 실행과 비교 방법

## 범위

- `AGENT_READ_CONCURRENCY=3` (기본): 한 단계의 독립 조회를 최대 3개 동시 실행한다. 1이면 순차, 허용 범위 1~8.
- collect: LLM이 같은 응답에서 선택한 조회 도구들을 병렬 실행한다. 별도 LLM 턴 사이에는 병렬화하지 않는다. mock/비교 실행은 필수 7종을 고정 호출한다.
- 같은 collect 실행에서 성공한 도구 결과는 재사용한다. 같은 LLM 배치의 동일 도구/인자는 한 번 실행한다. 실패는 다음 배치에 캐시하지 않으며 회사 ID 검증은 캐시 확인 전에 수행한다. 사용자·작업 사이 공유 캐시는 없다.
- retrieve: 성숙도 공통 근거를 먼저 조회한 뒤, 요청 범위 업무별 검색을 병렬 실행한다. 검색어·top_k=5·기존 중복 제거 규칙은 유지한다.
- 결과 취합과 LLM ToolMessage 순서는 입력 순서를 유지한다. 공통 실행기는 오류/취소 시 진행 중 형제 작업을 취소하고 종료를 기다린다.
- 평가·선행 관계·저장·승인 등 의존 관계가 있는 흐름은 기존 순서다. FE/BE 수정은 없다.
- 실제 Gateway TOOL_END 이벤트와 내부 노드 trace에 durationMs를 추가했다. 도구 시간은 시작 이벤트 전부터 종료 이벤트 전까지로 MCP 연결·재시도와 시작 콜백을 포함한다. 노드 시간은 해당 노드 전체를 포함한다.
- 제한은 작업/단계별이다. 프로세스 전체·배포 인스턴스 전체 제한은 아니다. 동시 사용자 증가 시 MCP/DB 연결 수를 고려해야 한다.

## 측정

```bash
# .env와 동일한 MCP 설정으로 실행; 쓰기/승인/상태 콜백/LLM 호출 없음
python scripts/benchmark_agent_reads.py --live --rounds 3 --output .local/reports/read-concurrency/live.json
# 네트워크 없이 fixture 결과 확인 (실제 성능 측정이 아님)
python scripts/benchmark_agent_reads.py --rounds 3
```

순차(1)·병렬(3) 실행 순서를 회차마다 바꿔 각각 3회 측정하고 중앙값을 비교했다. 로컬 Spring/MCP/PostgreSQL 및 실제 OpenAI 검색 임베딩을 사용했다. 초기 7개 조회는 고정 실행하여 LLM 계획 시간/변동을 제외했다. 검색 임베딩은 비용이 발생할 수 있다. JSON SHA-256으로 7개 조회 원문과 취합된 검색 결과의 순서·내용을 비교하며, 보고서에는 근거 원문을 기록하지 않는다.

| 구간 | 순차 중앙값 | 병렬 중앙값 |
|---|---:|---:|
| 초기 7개 조회 | 0.1340초 | 0.1079초 |
| 공통 근거 + 업무별 검색 | 1.6235초 | 0.7125초 |
| 전체 읽기 구간 | 1.7576초 | 0.8205초 |

읽기 구간은 약 53.3% 단축(2.14배), 모든 6회 결과 해시가 같았다. 환경·네트워크·캐시에 따라 달라지며 전체 Agent가 2.14배 빨라졌다는 뜻은 아니다. LLM·평가·저장·승인은 이 측정에 포함하지 않는다.

자동 회귀는 순차/병렬의 회사·지표·후보·근거·포트폴리오·로드맵·답변을 동일 fixture/MockReasoner로 비교한다. 실제 LLM 문구는 실행마다 달라질 수 있고, 원본 데이터/색인이 변경되면 읽기 결과도 달라질 수 있다. Spring 계산 입력이 같다면 점수·조합은 동일해야 한다.

기존 실행 프로세스에 환경변수와 코드 변경을 적용하려면 Agent를 재시작한다. MCP·BE·FE 재시작은 필요 없다.

## 회귀 결과

- 자동 테스트: 155 passed / 29 skipped (별도 환경 필요 검사).
- 실제 OpenAI LLM + FE 프록시 → Spring → Agent → MCP → PostgreSQL: 시드 분석·승인·프로젝트 등록 DONE. 선정 (207,507), (208,508), (209,509), AX점수 합 265, 비용 295,000,000원 유지.
- 실제 trace에서 collect와 retrieve의 도구 동시 실행 최대값이 각각 3임을 확인했다. 도구/노드 소요 시간 기록도 확인했다.
- 해당 실제 LLM 실행 전체는 승인·저장 포함 16.88초였다. 전체 실행의 순차 대조군을 동일 조건에서 측정한 것은 아니므로 이 숫자로 전체 성능 향상을 주장하지 않는다.
