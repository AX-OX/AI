# RAG 검색·근거 ID 개선 및 단계별 검증

2026-10-22, `agent-enhancement` 로컬 작업 기준. BE `main` c03c15d, FE `main` 3bd3962 소스는 변경하지 않았다. 실제 테스트는 로컬 PostgreSQL 55449의 샘플 DB, 실제 MCP, OpenAI LLM/Embeddings API를 사용한다. GCP 배포·운영 DB 검증은 아니다.

## 1. 공통 문서 top_k 확대

유형별 검색을 3개에서 5개로 늘려 실제 MCP로 비교했다. 빠졌던 개인정보 처리·업무 연결·표준화 점검·가상 사전 실험을 모두 검색했다. 전체 34개가 조회돼도 최종 30개 제한에서 일부가 탈락함을 확인했다. 이 임시 방식은 3단계의 일괄 조회로 대체했다.

## 2. 입력 분리와 보존

전역 `unique[:30]`을 제거했다. 성숙도 근거와 업무 근거를 별도 State 필드로 보관하고, assess/discover/respond 입력을 목적에 맞게 구성한다. 평가 근거 본문이나 직렬화된 JSON 문자열을 자르지 않는다. 각 단계의 문자 예산을 넘으면 명시적 오류를 반환한다. collect의 도구 결과 길이 제한은 기존 Harness 정책으로 유지한다.

2단계 실제 MCP 조회에서 전체 34개 보존과 관련 회귀 검사 56개 통과를 확인했다.

## 3. 성숙도 조회와 업무 의미 검색 분리

- 새 RAG 도구 `get_assessment_evidence()`: 활성 회사·색인 범위에서 정책·시스템·AI 현황·데이터 품질·프로젝트 보고서의 전체 섹션 조회. 검색어 임베딩 API는 호출하지 않는다. 200개를 초과하면 부분 진단을 하지 않고 오류를 반환한다.
- 현재 코퍼스의 공통 근거는 19개다. 모델·revision·corpus hash 검증과 회사 범위 제한을 기존과 같이 적용한다.
- 업무 매뉴얼은 요청 범위 업무별 `search_docs(top_k=5)`로 의미 검색한다. v3에서는 문서 한 개가 여러 업무를 담으므로 업무 번호가 일치하는 섹션을 우선 사용한다. 새로운 형식의 문서는 이 번호 규칙 대신 명시적인 청크별 업무 연결 계약이 필요하다.
- 전체 요청: 1회 공통 조회 + 9회 업무 검색 = RAG 10회, 실제 사용 근거는 공통 19개 + 업무 9개.
- 개발팀 요청: 공통 19개는 회사 진단용으로 유지하고 업무 검색만 3회 = RAG 총 4회.

실제 조회에서 이전에 빠진 4개 섹션을 모두 확보했다. 성숙도 기본 입력은 실패 작업의 26,740자에서 12,496자로 감소했다. 이후 rubric·근거 ID를 추가한 최종 입력은 14,801자다. 문자 수이며 토큰 수가 아니다.

## 4. 근거 ID와 검증

LLM이 문서 ID·섹션을 생성하는 대신 제공된 E001 등의 ID를 선택한다. JSON Schema enum과 strict Structured Outputs를 사용하고, Agent가 원래 문서·섹션으로 복원한다. [OpenAI 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs)

실제 LLM 평가 전에 기존 `maturity_criteria.yaml`의 세부 자체 기준표도 연결한다. 가중치와 Spring의 총점 계산은 변경하지 않는다. 근거 오류는 영역 누락·알 수 없는 ID·영역에 맞지 않는 문서 등으로 구분해 메타데이터만 추적한다. 인용·영역 연결 오류만 최대 1회 보정하며 실제 정보 부족은 null과 missing_reason으로 유지한다. 점수를 강제로 채우지 않는다.

실제 OpenAI 성숙도 평가 3회 모두 5개 영역과 유효한 문서·섹션을 반환했다. 보정 0회, 3.59~5.24초. 원본 프롬프트·키는 보고서에 기록하지 않는다.

## 5. 전체 연동 검증 중 추가 보완

첫 반복 실행에서는 성숙도 오류는 재현되지 않았지만 후보가 7~8개로 달라졌고, 개발팀 질의에서 process_id=208과 solution_id=509의 잘못된 조합이 검출됐다. 이를 통과시키지 않고 중단했다. 중간 결과는 Git 제외 로컬 보고서에 보존했다.

후보도 카탈로그의 S501 같은 ID로 선택하고, 업무·솔루션 ID를 코드에서 복원하도록 보완했다. B001 같은 후보별 허용 근거를 선택하며, 근거가 있는 요청 범위의 전체 평가 후보가 포함됐는지 검사한다. 누락·잘못된 연결만 최대 1회 보정한다. 없는 근거나 범위 밖 후보는 만들지 않는다. 최대 10개 후보 제약을 넘으면 범위를 나누도록 오류를 반환한다. Spring의 계산·최적화와 최종 승인 경계는 유지한다.

## 남은 범위

- 청킹은 기존 섹션 단위, overlap 없음으로 유지했다. 벡터 입력은 변경하지 않았으므로 이번 검색 개선 때문에 재임베딩할 필요는 없다.
- 실패 단계 하이라이트는 기존 FE가 도구 이벤트 중심으로 표시한다. 새로운 노드 이벤트를 도입하려면 BE·FE와 계약 합의가 필요하다. 가짜 도구 이벤트로 진행 단계를 만들지 않았다.
- 성숙도 총점은 기존 Spring 응답에 없어 차트를 생략한다. 성숙도 단독 요청도 아직 전체 로드맵 흐름을 실행한다.
- 대규모·긴 문서는 근거 조회의 페이지·범위 분리 및 단계별 입력 예산 설계가 필요하다. 문서 업로드 트리거·Cloud Run 배포는 이번 범위에 포함하지 않았다.
